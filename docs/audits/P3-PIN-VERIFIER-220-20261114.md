## Threat model and implemented behavior

This module is a **local PIN verifier, not authoritative authorization**. A separately authenticated account/device session MUST supply a fresh high-entropy, non-extractable HMAC-SHA256 key. The key is not persisted with the PIN material; it must come from an already-verified key hierarchy. No unsafe fallback derives it from a short PIN or stores it in IndexedDB.

- Normal PIN: 4–8 ASCII decimal digits. Optional emergency PIN: same length, different value.
- Each role has independent random 256-bit PBKDF2-SHA256 salt, 600k iterations, and HMAC-SHA256 over a domain-separated account/device/role binding. Stored rows contain only salts and keyed tags, never a PIN, derived bits or HMAC key.
- The first enrollment uses atomic IndexedDB add. Re-enrollment over an existing PIN row is denied, so merely reopening a tab cannot reset lockout or overwrite a verifier.
- Candidate tags are computed outside IndexedDB transactions; each attempt is resolved and accounted within one atomic Dexie read-write transaction to avoid losing concurrent failures. Five misses lock for 30 minutes; successful normal entry resets failures. Emergency entry yields a distinct **intent** result, NEVER wipes keys or triggers cloud operations.
- Device time rollback yields a fail-closed status, not an automatic unlock. The attempt budget persists over application module reload because it is IndexedDB state, not a volatile variable.
- PIN verification does not return or expose Recovery Key, media keys or plaintext. A missing or corrupted verifier is an error, never unprotected entry.

## 2026-11-14 — HMAC-authenticated local lockout ledger (CHAT-E, Draft #308)

**Additional security finding:** the first isolated verifier stored `failures`, `lockedUntilMs` and `lastObservedMs` unprotected; an offline IndexedDB edit could clear the 5-failure lock. The new version signs a canonical, domain-separated array of account/device IDs, verifier revision, salts, keyed PIN tags and mutable lockout fields using the external non-extractable device HMAC key. A wrong secret, direct counter edit, changed salt/tag or unsigned legacy record now fails closed before PIN evaluation.

**Atomic concurrency:** WebCrypto PBKDF2 and record HMAC are computed *outside* IndexedDB transactions. Each short Dexie rw transaction compares the entire previously authenticated record before writing a fresh MACed revision, retrying from a new verified snapshot after a conflicting tab update. After 12 justified conflicts, the operation fails closed rather than dropping failed attempts. Both normal and emergency matches remain distinct *intent statuses*, not active authorization or destructive operations.

**What remains unsafe/unproven:** an attacker with the ability to restore an old *complete valid* signed IndexedDB snapshot could roll back the lockout (no independently persistent trusted monotonic counter). Arbitrary same-origin JS with access to key operations is out of scope; a malicious device clock can be moved forward; clear IndexedDB yields explicit not-configured but is not tamper-proof credential storage. This must NOT be activated as a security boundary without a PIN-aware Identity lifecycle, protected pre-unlock keys, server-authoritative signed time and separate destructive flow acceptance.

**Identity integration preflight:** `apps/web/src/features/identity/application/session.ts` currently decrypts and activates local `PackageV2` before a successful online proof during `resumeLocalDevice()`, with `activeSession` retaining decrypted package for offline use. Therefore simply mounting the accepted PIN Shell screen over AccountView would not gate keys. No Identity, router, Shell, security UI or third-party files were changed in this PR; the signed PIN ledger is an isolated security primitive only.

**Negative test coverage:** 460/460 total including 11 direct PIN tests: five-failure 30m expiry, multi-tab CAS, reset of three counter fields, modified salt/tag, unsigned record, wrong device HMAC, clock rollback, format/equality, empty/corrupt record, no plaintext PIN. No real iOS/Android or OS secure element evidence.


## 2026-11-14 — independent two-layer PIN-sealed PackageV2 preparation (CHAT-E)

**Code SHA** `5cc99208d67e61b7cce72e6ea97dfd0567186217`. Main/base `6565a0fe852882ea5fc26e493df81affed687eee` remains unchanged. Newly claimed files: `apps/web/src/features/security/application/pin-sealed-package.ts` and `pin-sealed-package.test.ts`.

**Isolated implementation:**
- Seals genuine signed `PackageV2` bytes with PBKDF2-SHA256 600,000 rounds, 32-byte fresh salt, inner AES-256-GCM and second independent AES-256-GCM layer under non-extractable 256-bit device AES key; unique 12-byte IV for each layer.
- Both AEAD layers authenticate exact account/device, package revision, salt, IVs and domain purpose. Strict canonical/versioned bounded envelope. Rejects mismatched private/public P-256 signing keys, wrong revision, malformed, foreign or tampered data.
- Serialised envelope does not carry account private signing key/AKEK plaintext. Source clear byte buffer and intermediate ciphertext buffers wiped after crypto; returned `PackageV2` and JS strings cannot be reliably wiped.
- Only standard app PIN can decrypt the envelope; emergency PIN is never an unlock or destructive action.

**Critical limitations (NOT ACCEPTED):**
1. **UNWIRED**: current `resumeLocalDevice()` still decrypts and activates a `PackageV2` before a PIN. Full Identity/bootstrap redesign must withhold live keys before displaying PIN Shell; a screen overlay alone is NOT a security boundary.
2. The sealed-package primitive does not by itself enforce the HMAC-protected 5-failure lockout ledger. Future caller needs verified trusted enrollment and atomic PIN check before opening. Exported crypto helper is not resistance to arbitrary same-origin JS or offline repeated guesses with a usable device key, particularly for 4-digit PIN.
3. An expected revision supplied only by the caller is not a trusted anti-rollback source. Complete old signed IndexedDB snapshots, device-key lifecycle, independent secure clock and revoked-device acceptance require separate protocol and QA.
4. Browser credential custody and local-storage deletion/eviction, authorized change/disable and full Panic/Recovery Vault preservation, real iOS/Android and integration E2E NOT IMPLEMENTED/NOT TESTED. Never activate or merge as production PIN security until independently reviewed.

## 2026-11-14 — guarded PIN-verifier → PackageV2 admission (CHAT-E)

**New EXCLUSIVE files** `apps/web/src/features/security/application/pin-package-admission.ts` and `pin-package-admission.test.ts`; prior PIN primitive, encrypted-package code and production Identity left untouched. This is a pre-integration helper, not active session security.

The helper requires a caller-supplied, separately authenticated, synchronously readable `TrustedPinContext` with exact accountId, deviceId, pinned packageRevision and per-authenticated-session nonce. It takes a frozen scalar copy before async work. It calls existing HMAC-authenticated 5-failure/30-minute PIN verifier, rechecks same context after the PIN operation, admits only `app-unlocked` to the AES-GCM envelope decrypter, rechecks the context again after decryption and ensures decrypted package ID/revision match. Invalid/locked/clock rollback return status with NO key; emergency PIN yields a non-destructive `emergency-intent` and cannot open the package. If the identity changes after the verifier or during unseal, the helper fails closed instead of returning a package.

**Observed security hazard fixed in own code:** a caller may reuse and mutate the same trusted-context object while an async PBKDF2 step runs. An unfrozen referenced snapshot would compare the object to itself after mutation and allow a stale session. The helper snapshots and freezes scalar fields; a negative test specifically mutates sessionNonce in place before its second read.

**Accepted disposable-device test scope, no live activation:**
- Uses actual `pb3-identity-v2` schema v3 and its persisted `devices` object store. Preflight reads `devices`, `pending`, `recoveries`, `pairings`, `rotations`, `sessions`. Requires no active volatile `activeSession`, exactly one local device for account and no uncompleted registration/pair/recovery/rotation or signed-out state capable of retaining legacy access.
- Decrypts original real DeviceEnvelope using nonextractable device AES key, checks full PackageV2 against caller-supplied value, verifies device P-256 private/public signing-key consistency, then produces PBKDF2/AES-GCM + nonextractable AES-GCM doubly protected PIN package.
- Enrolls HMAC-authenticated PIN verifier in the separate Dexie IDB, checks correct app PIN, and conditionally replaces ONLY original `devices[deviceId].envelope` with `pinMode=pin-v1` ciphertext plus nonextractable device HMAC key. All pending device-row reads and the replacement share a single short IndexedDB `readwrite` transaction. Competing migrations are refused and cannot leave a second plaintext legacy envelope from this device.
- After a disposable swap, original `openDevice` fails, `readSealedPinDevice` retrieves encrypted metadata and the previously unit-tested guarded admission decrypts only after ordinary PIN. Emergency input gives INTENT only; no deletion.
- Tests prove no-write on wrong account or mismatched real PackageV2, secondary local device, unresolved registration without accountId, recovery/pairing/rotation, active volatile session or signed-out state; two parallel migration attempts leave exactly one sealed device, no residual legacy read, and simulated PIN-verifier eviction fails closed without downgrade. No production records are touched by tests.

**Security blockers — NOT PRODUCTION READY:**
1. **NO automatic enrollment or route wiring:** existing `resumeLocalDevice()` still decrypts legacy packages before PIN. A sealed-device row instead causes existing loader to fail closed; an accepted guarded PIN-aware bootstrap is required to log in or unlock it. Current module MUST NOT be called on an actual user device.
2. **Cross-DB atomicity impossible as written:** PIN verifier resides in distinct `pb3_pin_verifier_v1` IndexedDB database; device envelope in `pb3-identity-v2`. If a browser crashes between verifier creation and device transaction, orphan verifier remains and legacy state is still available. If verifier data is later evicted, a sealed device remains locked. Recovery Key remains mandatory; no silent local fallback. A single authoritative atomic schema or reviewed recovery/reconciliation workflow is needed before enrollment.
3. **Volatile and multi-tab session race:** checking `activeSession.value===null` does not guarantee no pending `resumeExistingDevice()`, other window, or retained in-flight decrypted package. Security requires a cross-tab pre-migration barrier and global one-way session invalidation/flush/wipe of stale in-memory state. No such mechanism is asserted by this module.
4. **Recovery authentication and key custody:** caller's provided PackageV2 is matched against local device but does NOT prove a fresh server challenge or Recovery Key possession. Nonextractable browser `CryptoKey` can still be used by same-origin code; 4-digit PINs remain vulnerable to offline enumeration if an attacker can invoke key operations. No trusted server/device time and complete IndexedDB rollback prevention, no PIN change/disable, no signed Panic/revoke.
5. **Native device QA NOT TESTED:** iOS Safari/Android WebCrypto structured-clone, IndexedDB browser eviction/reload and recovery after crash require physical acceptance. The `readSealedPinDevice` metadata read is not an authenticated session.
