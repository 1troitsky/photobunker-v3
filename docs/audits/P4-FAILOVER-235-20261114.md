## What is implemented (isolated, unmounted)

New App\Storage\Failover\ReplicaReadPreflight::inspect:
1. Trusted server-side account, asset and location IDs. No browser-supplied object path, endpoint, credentials or provider registry. Supports live photo objects and media chunks.
2. Read-only canonical DB check: account ready, parent and asset active, TTL not expired, tombstone absent; two distinct locations, matching logical ciphertext SHA/byte count, verified replica state.
3. Trusted server-owned adapter registry requires distinct providers and declared failure domains and positive credential revisions. Distinct labels are not proof of administrative or geographic independence.
4. Reads only replica transport (primary can physically be unavailable), verifies exists/size/full-stream SHA-256 with 8MiB hard cap and discards the ciphertext; no writes, status promotion, pointer changes or plaintext access.
5. Rechecks canonical DB after physical IO for revoke/delete/TTL/location changes. Errors fail closed and sanitize adapter exceptions.
6. Returns status=replica_physical_preflight_only, physicallyVerified=true, failoverAuthorized=false. No browser route or StorageManager invocation is wired.

**Security limitations:** The readback observes a state at two times, not an atomic signed receipt or production authorization. A later write, expiry, deletion, credential rotation, provider failure-domain misconfiguration or concurrent assignment of a new active generation can invalidate it. Actual failover must implement account-scoped generation fencing, signed receipt/credential rev checks, recheck on the live read path, ACL and privacy-safe status. The initial source-only stage had no real provider outage evidence; a NEW dedicated 7/7 two-Garage CI stage now verifies actual stopped-node readback as documented below, but it still does NOT activate the StorageManager production read path or establish signed receipts and real customer failover.

**Discovered observable gap:** the earlier snapshot fingerprint considered the parent/asset/account and location field values and timestamps, but a successful committed **ABA** could change verified→reserved→verified or active→deleting→active without changing those values or updated_at. A physical ciphertext SHA check cannot identify this metadata race.

**Bounded defense in the internal, still-unmounted preflight:** for PostgreSQL18, fetch and compare system MVCC tuple identifiers (xmin as text) alongside all existing values for each row: identity_accounts, photo_records/media_files_v1, photo_objects/media_chunks_v1, and *both* storage locations. A missing or invalid PG tuple witness fails closed. Read-only verification does not retain a DB transaction or row lock during S3 I/O, cannot sign a provider receipt or claim a durable generation. SQLite feature tests deliberately get NULL tuple-witness columns and only exercise the existing contract; they are **NOT** proof of ABA protection. PostgreSQL xmin is a bounded same-row change detector during a single call; wraparound, VACUUM freezing, delete/recreate, tombstone insertion/deletion, provider trust and longer production lifecycles still need durable append-only versions and writer/reader fencing.
