## Code in this PR

1. **Migration:** remote_wipe_commands, globally unique target-device operation and operation UUID, immutable account/actor/target/revision plus signed command evidence. Successful insert requires target already revoked; this service does not revoke it.
2. **Domain:** App/RemoteWipe/SignedDeferredCommand with exact versioned device-local-only wire payload, account-root and active actor-device P-256 signatures, server-authenticated actor/account binding, account→actor→target transaction locks and strict revision validation.
3. **Idempotency:** exact signed retry preserves one operation; new operation for same target and altered original digest fail closed (409).
4. **Target receipt:** only the original target signing SPKI signs a separate domain-separated receipt tied to original SHA-256 and operation/account/target. A duplicate signed self-report is idempotent. **A signature does not independently prove physical local erasure.**
5. **Honest statuses:** wipe_pending vs target_reported_local_wipe, always localWipeProven=false, matrixRemoteRevoked=false, cloudDeleted=false, backupDeleted=false. No S3, Recovery Vault, Matrix or unrelated device mutations.

## NOT RELEASE-READY

- **No HTTP route** is mounted. A revoked target cannot yet receive/poll/acknowledge the command through a verified bounded delivery transport; browser/local executor is missing.
- Revocation (#80) and durable command insertion are **not yet atomic**. Once the signed #80 path has passed acceptance and integration is authorized, join revoke+persist in one transaction. A non-atomic gap must never count as completed Remote Wipe.
- The browser must require explicit target confirmation and trusted session, maintain an encrypted durable command/outbox, deny offline false success and report lost ACK honestly.
- Full remote Matrix token revoke requires separate homeserver authority. **Ordinary device revoke must preserve Recovery Vault and account media**.
- A compromised target signing key can forge a self-reported wipe; do not transform receipt status into certified physical erasure.
- Genuine PostgreSQL18 two-PHP-process signed-command races have been **verified 3/3** on the exact own test code; still missing are atomic integration with #80 signed revoke, cross-device offline delivery/actual local wipe and physical iOS/Android.

## Signed revoked-target delivery: UNMOUNTED verified read-only server domain

**New code + test + workflow SHA:** `1747f21d8b29a7175eee9a709830d8e215de509a`; all three NEW OWN paths are `apps/api/app/RemoteWipe/SignedRevokedDelivery.php`, `apps/api/database/migrations/2026_11_14_000321_create_remote_wipe_delivery_proofs_v1.php`, `apps/api/tests/Feature/RemoteWipe/SignedRevokedDeliveryTest.php`. Only existing OWN `.github/workflows/p3-remote-wipe-222.yml` was also modified; no other owner's branch, routes or controller touched. Source purpose: allow a **previously revoked target** holding its original, strictly bound P-256 signing key to request only its original signed `wipe_pending` command. This is **not** a PB3 login, grant, recovery-key exchange, device reactivation, remote wipe execution or HTTP route.

Server verifies exact canonical domain-separated `pb3.remote-wipe-poll.v1` request with unique UUID `requestId`, 32-byte unpredictable nonce, target/account UUIDs and ±90-second issuedAt clock check, then validates signature with original revoked device's DB-backed signing SPKI. It locks account→target→command, requires current authoritative `revoked_at`, original pending signed command, validates canonical command bytes and SHA256 against persisted signed command, and returns only original payload/root+actor signatures plus explicit `sessionGranted:false`, `localWipeProven:false`, `cloudDeleted:false`, `backupDeleted:false`, `matrixRemoteRevoked:false`. A client must independently verify original root/actor signatures against its previously trusted historical keys, especially after Recovery Key/key revision rotation; the server never substitutes the newest root into an old command. This code does not expose source media, keys, contacts, login session or a Matrix token.

A minimal `remote_wipe_delivery_proofs` table stores only request UUID, account/target/operation references, SHA256 of canonical signed poll bytes and server time; no raw nonce, token, recovery key or plaintext. Repeated request UUID returns 409; even distinct signed requests for the same device are limited to one per 15s with 429. Absent/unrevoked/cross-account/previously reported target gets 404; invalid signer gets 401; stale signed timestamp gets 401; malformed nonce/fields gets 422; changed command bytes/hash gets 409. **NOT YET RELEASE-READY:** automated retention / GC for old delivery-proof rows and HTTP CSRF/Origin/rate controls still need explicit integration and QA, even though per-target insert frequency is bounded.
