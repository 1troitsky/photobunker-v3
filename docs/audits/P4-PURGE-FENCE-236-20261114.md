## Security invariant

Deleting all physical copies requires keeping an irreversible record that **live** photo/media parent is no longer eligible for resurrection or a stale upload ACK. The existing temporary `photo_tombstones` / `media_tombstones_v1` tables may be swept or changed by old lifecycle implementations, so they cannot alone serve as a permanent owner-scoped read/write fence.

New `storage_purge_fences_v1` ledger uses one immutable row per `(account_id, kind, parent_id)`, where kind is `photo` or `media`, and intentionally stores **no provider object keys, plaintext, S3 secrets or E2EE key material**. Every row has a stable fence UUID, purge operation UUID, reason and server timestamp. No foreign key to the parent or account is included: their separate accepted deletion must not cascade-delete the immutable fence. This is a deliberate retention choice pending global account-erasure policy; potential indefinite metadata retention **requires privacy review**.

**Database immutability:** PostgreSQL18 `BEFORE UPDATE OR DELETE` trigger refuses changes even if PHP code issues direct SQL, and SQLite equivalent triggers protect tests. Parent uniqueness and `lockForUpdate` on the canonical parent serialize concurrent accepted purge intents. Same operation+reason is idempotent (Lost ACK replay returns same fence ID); a different reason or operation on already-fenced parent fails closed. Same Panic operation UUID may legitimately cover more than one parent. Account/parent/kind are checked against canonical DB before inserting; a forged cross-account parent is refused.

**Security boundary:** `recordAuthorized` requires a trusted server-side caller that **already** verified signed owner/Panic/TTL authorization. It intentionally does NOT authenticate that decision or accept public HTTP requests. `isFenced` is only a read-only observation, not atomic authorization to upload, read or serve ciphertext. No StorageManager integration, write/ack fence, per-provider delete lease/receipt, replica GC, Recovery Vault accounting or panic wipe has been enabled. **No provider DELETE or real user content changes occurred.** The trigger prevents application SQL mutation, but a DBA/schema migration can still alter/drop it; it does not constitute an independent trust anchor.
