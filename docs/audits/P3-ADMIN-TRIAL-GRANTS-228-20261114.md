### Fail-closed PG18 CLI QA harness hardening

The new cross-action physical race script exposed a subtle GitHub Actions **false-success** risk: after Laravel console bootstrap, throwing an uncaught `RuntimeException` can be logged as a Laravel error while the CLI process returns status **0**. Successful output markers alone are not enough to declare an assertion-safe test job. The initial wrong-baseline cross-action error was preserved in [run #43560307334](https://github.com/1troitsky/photobunker-v3/actions/runs/43560307334). The new cross-action script already uses `fwrite(STDERR, ...); exit(70)` for every guard failure and passed [#43560464975](https://github.com/1troitsky/photobunker-v3/actions/runs/43560464975) with all five explicit success markers.

The two previously owned real-process scripts `apps/api/tests/integration/p3-admin-trial-postgres-race.php` and `apps/api/tests/integration/p3-admin-restriction-postgres-race.php` had the same dangerous `throw RuntimeException` guard and were independently hardened to explicit STDERR plus exit code 70; this is a QA-only correctness gate, not a change in billing, restriction, permissions or DB schema. Existing PHP/PDO/PG18 physical lock assertions are unchanged. The hardening ensures an assertion failure cannot masquerade as a green Actions step, and should be verified by successful explicit PASS markers under an exact-source commit CI.
