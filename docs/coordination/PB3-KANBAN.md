# PB3 — работа четырёх агентов через GitHub Kanban

**Назначение:** один общий список задач для трёх вкладок ChatGPT и локального агента, без постоянного разделения на Product/UX/QA.  
**Состояние на 12.11.2026:** создана документация и GitHub Issues, но **существование доски GitHub Project не подтверждено**. Не создавать вторую доску, если она уже есть.

## 1. Управляем разработкой через GitHub Issues

**Единый источник очереди работ — настоящие GitHub Issues, не отдельные черновики и не ручные карточки.** Готовая доска Projects может визуализировать Issues, но агенты не зависят от неё.

- [**Свободные задачи**](https://github.com/1troitsky/photobunker-v3/issues?q=is%3Aissue%20is%3Aopen%20label%3Aready) — метка `ready`; агент выбирает следующую после повторной проверки PR и зависимостей.
- `in-progress` — задачу занял агент, оставил комментарий с веткой, базой и затрагиваемыми путями.
- `review` — Draft PR создан и передан на тесты/интеграцию; сама Issue остаётся открытой.
- `blocked` — обязательная зависимость, которую нужно указать текстом в Issue.
- `epic` + `backlog` — большой функциональный раздел, а не готовое конкретное поручение.
- `meta` — организационная запись, не задача реализации.

**Одна задача — одна метка состояния** (`ready`, `in-progress`, `review` или `blocked`); при смене состояния прежнюю метку снимать. Метки `epic` и `backlog` могут сосуществовать как тип и стадия декомпозиции.

Задача считается свободной лишь когда имеет `ready` **и** агент после сверки живых PR подтвердил отсутствие пересечений. Если агент видит риск, он ставит `blocked` с причиной; не начинает конкурирующую реализацию. Одно активное Issue на агента.

## 2. Источники задач

- `ts.md` — полная спецификация, обязательные этапы P1–P4, критерии приёмки §25–27.
- `AGENTS.md` — инженерные правила, включая безопасность, Local-First и запрет самостоятельного слияния в `main`.
- `docs/ux/` — эталонные UX-файлы из PB2 PR #56; 117 файлов присутствуют в интеграционном Draft #158, **но не в текущем `main`**.
- `docs/_uiux/` — HTML-эталоны в `main`; их версии сверяются с утверждёнными UX.
- `docs/ux-integration/` — карта 22 экранов, переходов и сценариев на ветках #138/#158.
- `TS_PROGRESS_TABLE.md` — устаревшая приближённая оценка; не является доказательством готовности.
- [Карта эпиков](PB3-EPIC-MAP.md) — 16 функциональных направлений, но не список уже выполненных функций.

Оба каталога исходных макетов — `docs/ux/` и `docs/_uiux/` — не изменять автоматически. Если решение в UX обозначено WIP/OPEN, не выдумывать окончательную реализацию.

## 3. Эпик, задача и Draft PR

**Эпик** охватывает большой раздел продукта, например «Уведомления» или «Хранилище». Его статус не означает, что весь раздел реализован.

**Задача (Issue)** описывает один проверяемый результат, требования, зависимые PR, точный исходный SHA, разрешённые файлы и условия приёмки. Одна задача может ссылаться на несколько эпиков, но имеет один основной.

**Draft PR** содержит предлагаемое изменение. Успешный CI отдельно взятого PR не доказывает работоспособность общей сборки и не переводит весь эпик в Done.

## 4. Как использовать готовые колонки Kanban

**Основной сигнал для агентов — метка Issue**, а не произвольная колонка Projects.

- **Не начато:** задачу ещё предстоит сверить с кодом, её нельзя автоматически брать.
- **Можно брать:** требования, зависимости, актуальный исходный SHA и отсутствие пересечения с чужими PR уже проверены; это можно указать прямо в карточке, даже без отдельной колонки Ready.
- **В работе:** задача занята одним агентом; не более одной активной задачи на агента.
- **Проверка:** Draft PR готов, но приёмка или интеграция не завершена. При отсутствии отдельной колонки фиксировать это в Issue/PR.
- **Заблокировано:** конкретная причина с ссылкой на зависимость, а не расплывчатое ожидание.
- **Готово:** только после интеграционной проверки в согласованной базе, подтверждённых критериев приёмки и разрешённого слияния. Отдельно указывать непроверенные физические устройства.

## 5. Правила для всех четырёх агентов

1. Открыть актуальные `main`, `AGENTS.md`, `ts.md`, список открытых PR и задачу. Старые handoff и проценты готовности не заменяют живую проверку.
2. Выбрать свободную задачу, прошедшую проверку. До начала убедиться, что никто не занят ею и её файлами.
3. В Issue оставить короткую запись: **«Занято: Chat-1 / Chat-2 / Chat-3 / Local; ветка; исходный PR и SHA; что меняю; что не меняю»**. Снять с Issue метку `ready` и поставить `in-progress`.
4. Разрабатывать только в своей ветке; перед общими файлами согласовать владение. Не дублировать функции, уже реализуемые другим агентом.
5. Выполнить релевантные тесты на **точном HEAD**, не ослаблять E2EE, ACL, TTL, Local-First и другие защитные проверки.
6. Создать Draft PR, записать SHA, тесты, известные ограничения и статус интеграции. Затем заменить `in-progress` на `review` и взять следующую Issue с меткой `ready`.
7. Не сливать в `main`, не закрывать чужие PR и не выполнять развёртывание без разрешения владельца.

**Одновременные комментарии не дают атомарной блокировки.** Если два агента заняли одну карточку, второй прекращает работу по ней и выбирает другую. Приоритет имеет тот, чья запись появилась раньше, при условии что область работы не конфликтует с уже открытыми PR.

## 6. До проверки и слияния локальным агентом

- База `main` на момент составления документа: `da7327b8c9c440dae3dc864b3245b9f9f4ad14eb`. Перед работой повторно проверять актуальный SHA.
- [#158](https://github.com/1troitsky/photobunker-v3/pull/158) — интеграция UX/Product до V52; [#160](https://github.com/1troitsky/photobunker-v3/pull/160) — новые изменения редактора; [#162](https://github.com/1troitsky/photobunker-v3/pull/162) — отдельные исправления QA. Их совместное состояние пока не принято.
- [Issue #161](https://github.com/1troitsky/photobunker-v3/issues/161) закреплял прежнее разделение Product/UX/QA для уже начатых PR. Новые задачи распределяются по Kanban; старые границы владения не меняются задним числом.
- Не переписывать старые PR на основании нового эпика и не обновлять процент готовности без проверки.
- До объединения разрешены только изолированные, действительно независимые изменения.

## 7. Минимальные требования к новой задаче

**Результат:** один проверяемый сценарий.  
**Источники:** пункты `ts.md`, соответствующие `docs/ux/` и, если есть, S/N/J из `docs/ux-integration/`.  
**Зависимости:** исходный PR и точный SHA; разрешённые и исключённые пути.  
**Проверка:** тесты, сценарии offline/reload/retry, безопасность, реальные устройства — по применимости.  
**Передача:** ссылка на Draft PR, коммит, результаты CI, блокеры и то, что ещё не интегрировано.

## 8. После локальной интеграции

После разрешённого обновления `main` выполнить одну фактическую инвентаризацию (задача [#183](https://github.com/1troitsky/photobunker-v3/issues/183)): сверить цепочки PR, сопоставить функции с эпиками, сохранить исходные доказательства, убрать дубли и только затем отметить действительно доступные работы.

Главный принцип: **Kanban управляет очередью задач, а `ts.md` — обязательным содержанием PB3.** Количество закрытых карточек не заменяет готовность пользовательских сценариев.
