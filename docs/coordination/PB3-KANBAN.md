# PB3 Kanban — единый способ работы 3 ChatGPT + 1 локального агента

**Статус:** проектирование структуры 2026-11-12; **не** инвентаризация фактической готовности и **не** подтверждение создания GitHub Projects board.  
**Нормативные источники:** `ts.md` (все P1–P4 обязательны), `AGENTS.md`, `docs/ux/` (утверждённые источники в интеграционном дереве #158, НЕ в текущем main), `docs/_uiux/`, `docs/ux-integration/` (#138/#158), `TS_PROGRESS_TABLE.md` (историческая оценка, не источник готовности).  
**Текущая работа в существующих Draft PR сохраняется** и не считается слитой в `main`.

## GitHub Project

Имя: **PB3 — Development**. Один GitHub **Project** (Board + Table + Roadmap как представления *одних* items). Группировать Board по полю `Status`.

| Поле Project | Тип и значения | Назначение |
|---|---|---|
| Status | Single select: Backlog, Ready, In Progress, Review, Integration / QA, Blocked, Done | Единственное состояние карточки |
| Priority | Single select: Critical, High, Normal, Low | Выбор следующей задачи, не фазовая принадлежность |
| Phase | Single select: P0, P1, P2, P3, P4, Cross-phase | Гейты в `ts.md`; не обязательная последовательность выдачи |
| Epic | Text или parent issue / sub-issue | Контроль покрытия требований |
| Agent | Single select: Unclaimed, Chat-1, Chat-2, Chat-3, Local | Временная *занятость*, не специализация |
| Base | Text (PR URL + exact SHA) | Из какого проверенного среза ведётся работа |
| Blocked by | Issue/PR references | Реальные технические зависимости |
| Estimate | Необязательно | Спринты и жёсткие дедлайны не требуются |

Views:
- **Board / Work** — Status, фильтр: незакрытые карточки; отсортировать по Priority.
- **Table / Backlog** — Epic, Phase, Priority, Agent, Status, Blocked by.
- **Roadmap / Phases** — необязательный обзор P1–P4; отсутствие дат не должно блокировать работу.
- **Ready / Pick next** — Status = Ready, Agent = Unclaimed, Blocked by = none.

## Разница между Epic, задачей и PR

- **Epic** охватывает модуль из `ts.md`, но НЕ утверждает, что он реализован/не реализован; до независимой интеграции весь исторический статус `UNKNOWN / RECONCILE`.
- **Issue** — один проверяемый результат (вертикальный сценарий, feature slice или независимый технический блок), с links к `ts.md`, UX baseline и `J-xx/N-xx/S-xx` при наличии.
- **Draft PR** — изменение кода или документации; не означает Done. Исторические stacked PR не конвертировать автоматически в отдельные завершённые задачи.
- Задачи по P3/P4 можно начинать до формального закрытия P2, **только** если их конкретные зависимости и изменяемые файлы независимы.

## Колонки и критерии перехода

1. **Backlog** — сохранено в спецификации, но ещё не подтверждены base/пересечения/условия.
2. **Ready** — известны целевой результат, acceptance tests, source PR/base SHA; свободны files и нет блокирующей зависимости. Требует актуального preflight, а не одного текста Issue.
3. **In Progress** — *один* агент зарезервировал Issue/ветку/изменяемые пути и разместил claim-комментарий; максимум 1 In Progress на агента.
4. **Review** — Draft PR, список файлов, self-check и точный SHA готовы; недостающие проверки явно указаны.
5. **Integration / QA** — задача проверяется на объединённом дереве; CI отдельных PR недостаточно.
6. **Blocked** — конкретная причина, ссылка на блокирующий PR/Issue или требуемое решение; не «ждём на всякий случай».
7. **Done** — только после проверки согласованной объединённой версии и интеграции в выбранный целевой baseline; для `main` требуется отдельное согласие владельца, а UX/manual/mobile gates не подменяются CI.

**Готовность PB3 = выполнение P1–P4 и `ts.md` §25–27**, а не количество карточек Done.

## Как любой из четырёх агентов берёт работу

1. Сначала актуальные `main`, `ts.md`, `AGENTS.md`, карточка и GitHub PRs; проверить `Files changed`, SHA, ancestry, owning agent. Старый handoff и `TS_PROGRESS_TABLE.md` не заменяют свежие факты.
2. Выбрать **Ready + Unclaimed** с наибольшим приоритетом и подходящими зависимостями; до старта ещё раз проверить, что задачу не забрали.
3. Написать в Issue `CLAIM: Chat-1|Chat-2|Chat-3|Local; branch: ...; base: PR#... @ SHA; scope: ...; excluded: ...`; поставить Agent, Status=In Progress. В отсутствие Projects редактировать статус в комментарии, но комментарии **не гарантируют атомарную блокировку**: при коллизии второй агент уступает.
4. Ветка и Draft PR отдельные; не менять `main`, чужие ветки, общие runtime файлы без явного согласованного переноса владения. Не открывать второй PR, дублирующий функцию уже существующего.
5. Тесты на точном HEAD. Протокол E2EE/ACL/Local-First/TTL/Security не ослаблять; не выдавать макет за работающую интеграцию.
6. Указать точный commit/CI/evidence/блокеры в PR и Issue; перевести в Review/Integration и занять следующую *независимую* Ready.
7. Отдельный интеграционный шаг сверяет последнюю продуктовую цепочку + UX #158 + QA потомков, проверяет сводные E2E и готовит `main` только по разрешению.

## Карточка Issue — минимальный контракт

```md
## Результат
Один проверяемый сценарий / инкремент.

## Источники
ts.md §...; docs/ux/... / docs/_uiux/...; UX map S__/N__/J__ (если применимо).

## Dependencies / preflight
Existing PRs and HEAD; exact base SHA; paths allowed/excluded.

## Acceptance
- [ ] Correct behavior on real persistence/API where required, no demo bypass
- [ ] Offline/reload/retry, ACL/E2EE/TTL if applicable
- [ ] Unit/E2E/CI on exact HEAD; untested device gates stated explicitly

## Delivery
Draft PR, commit SHA, CI results, evidence, blockers, next task.
```

## Следующий обязательный шаг после локального агента

Проверить объединённый `main` и ancestry старых Draft PR, обновить статус каждой существующей функции `NOT STARTED / PARTIAL / VERIFIED / INTEGRATED`, связать существующие Issue/PR с Epic, удалить дубли только после проверки, поднять в Ready действительно свободные инкременты. **Не проводить сейчас ложную «полную инвентаризацию» по одному старому main.**
