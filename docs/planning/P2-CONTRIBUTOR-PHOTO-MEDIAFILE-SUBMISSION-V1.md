# P2 — Contributor-signed imported Photo MediaFile assignment receipt (v3)

**Status:** Draft, no merge into `main`. Parent #110: full exact-head 6/6 CI, 40/40 Chromium, 245/245 Vitest, 142/142 PHPUnit.

## Precise claim, not a fake camera attestation

An invited, accepted assignment contributor who owns a synced, encrypted **P2 Photo MediaFile** can explicitly grant its assignment owner the recipient-specific E2EE key for **that entire file** (including its private metadata) and sign a distinct assignment submission receipt. This establishes **which account authorized which encrypted photo for which assignment**, never proves a physical camera took it at a particular place/time. Imported P2 photo is marked `capturedInAssignment=false`, even though the contributor signed the submission. This intentionally does **not** replace the already-operating P1 legacy `photo_records` camera and photo grant flow.

## Contract and defenses

- Only `version=3`, `kind='photo'` is accepted by the new `pb3.assignment-media-submit.v3\n` account signature domain. Exact canonical signed JSON: `version, submissionId, operationId, assignmentId, contributorAccountId, mediaId, mediaGrantId, mediaContractHash, policyRevision, policyHash, kind`. No capture proof fields may appear.
- The server checks a currently active accepted *contributor* invite, current owner-signed assignment policy (root v1 photo-only or independently signed amendments), schedule and open retention, policy revision/hash, exact contributor-owned active P2 Photo MediaFile/hash and live TTL. Private category/description/GPS/tags stay E2EE; preflight on the contributor's own device decrypts metadata and checks current owner-signed photo recording/advanced rules before any DEK is wrapped.
- **Mandatory v2 assignment-scoped E2EE grant**, separately signed by the contributor using `pb3.media-grant.v2\n` and addressed to the verified assignment owner. The server enforces `grant.assignmentId===submission.assignmentId`, `version=2`, `scope='read'`, exact contribution/photo/grant IDs, immutable SHA-256 MediaFile hash, recipient identity, expiry and account signature. **Neither a personal v1 media grant nor an owner editorial link (#110) is sufficient**. Revocation, file archive/expiry or assignment retention cutoff denies future reads. Already downloaded/decrypted copies cannot be recalled.
- The original source media remains contributor-owned, independently encrypted and unchanged. No transfer of control, Public Card link, anonymous key or public metadata. It does not attach the photo to owner's private Safe editorial link and does not turn metadata-ceiling flags into public permissions.
- Existing private authenticated `assignment_media_submissions_v1` now also accepts `photo` receipts. Owner read-only submissions pagination returns `mediaType='photo'`, `capturedInAssignment=false`. Server-authoritative confirmedPhotoCount sums **distinct legacy photo_records** and **live P2 Photo MediaFiles with explicit assignment-scoped E2EE grants**, not locally queued operations; revocation decrements the current displayed count but signed historical receipt remains. Video/audio unaffected.
- Browser/Assignments shows imported Photo MediaFiles distinctly from legacy camera shots, confirms handing over a **complete encrypted file DEK and its private metadata**, including GPS if present; owner decrypts the JPEG only on their own device using the independently pinned sender exchange key.
