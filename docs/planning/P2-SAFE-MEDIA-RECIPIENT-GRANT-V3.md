# P2 Safe / Original — account-to-account signed recipient scope (v3)

**Status:** Draft implementation candidate; exact-head Chromium/PostgreSQL18/Garage and PHP 8.4/8.5 CI are mandatory. **Public Card/anonymous URL is OFF.** Original source share and the current v1/v2 per-file E2EE grants are preserved as independent, explicit operations.

## Source of truth and design rationale

`ts.md` §4, §5, §13 and §18 specify independent photo assets/versions, explicit per-recipient scopes and wrapped DEKs, safe flattened output without EXIF/GPS, assignment∩file∩grant∩TTL intersection and a revocable token for eventual public links. The exact public token/key transport is an explicitly unresolved **OPEN** decision. The preceding photo editor Draft #105 produces a separate owner-encrypted JPEG with opaque black pixels, not an automatically safe public publication.

The old `pb3.media-grant.v1/v2` signed contract grants `read` for **one MediaFile ID**, with no source/derivative relationship. Merely relabelling a read grant to "Safe" is unsafe because it could wrap the ORIGINAL's DEK. We add a distinct domain-separated **`pb3.media-grant.v3\n`** signed `safe_read` contract instead of overloading existing scopes.

## End-to-end scope

1. The owner creates a separate local JPEG using the actual Viewer. Adding at least one opaque blackout enables an **explicit owner opt-in** to mark that new encrypted personal copy as a *candidate* for recipient-only Safe sharing. A small, account-scoped local index records only the owner account UUID, source MediaFile UUID, derived MediaFile UUID and immutable SHA-256 hashes of both signed media contracts. **No plaintext image, EXIF, GPS, edit geometry, media description or DEK** is put in that index.
2. No grant is created by preparing, labelling or syncing a candidate. Both source and derivative must exist as distinct, **synced**, unexpired **photo** MediaFiles owned by the active account; a stale, changed or missing source/safe contract hash fails closed.
3. For a **manually fingerprint-verified recipient**, the owner explicitly confirms sharing the selected candidate. A new P-256 ephemeral ECDH/HKDF AES-GCM envelope wraps **ONLY the independently random DEK of the derived MediaFile**, with domain/AAD bound to recipient+owner account IDs, grant UUID, source+derived media IDs, **both exact media contract hashes**, expiry and `scope=safe_read`. Original DEK and chunks are never included in the envelope. Owner signs the full canonical v3 contract using the existing root signing key. Outbox stores only signed contracts and wrapped key ciphertext.
4. Backend v3 creation verifies account/device actor, owner signature under its distinct v3 domain, active ownership of **both** records, media type photo, distinct IDs, contract hash consistency, no archives/deleting, real recipient exchange directory, max 24h grant and **expiry <= both source and derivative TTL**. It records the signed source reference alongside the source-bound grant. Neither client-provided S3 object keys nor a server plaintext operation is accepted.
5. On every subsequent recipient manifest/**physical chunk** read, the service rechecks the grant, source and derivative states, TTLs, source contract hash, recipient account and any archive state. The chunk query uses **only `grant.media_id` (derived file)**; asking for any original chunk UUID with the same grant ID returns 404. Recipient independently verifies pinned owner's signature, exact v3 contract schema, media hash/receipt and the envelope AAD, and decrypts **only** the derived JPEG. Received list explicitly distinguishes `safe_read` from ordinary `read`.
6. Existing signed revocation revokes the grant and blocks subsequent server reads. It does **not** erase ciphertext/plaintext previously downloaded by a recipient. The original remains immutable and accessible **only through its own previously authorized scopes**; the v3 grant grants no original right. No implicit grant from contacts/teams/assignments.
7. The feature is **recipient-only** and non-public. The user must still review the masked image. A black rectangle is not proof that every possible sensitive detail was covered, that prior recipients lack the original, or that an arbitrary other original copy can be cryptographically recalled. No safe-publication/public-card feature is enabled, and the exact safe public token/DEK delivery policy remains **OPEN**.

## Verification / gate

- PHP feature: cross-account unauthorized source access, valid v3 grant, idempotence, source chunk 404, derived chunk 200, dynamic source expiry/forged hash/wrong ownership/wrong scope/extra fields/wrong type and negative rollback.
- Vitest: exact v3 schema and distinct source/derived IDs, reject `scope=read|original|public`, unrecognized fields and missing hashes; old v1/v2 unchanged.
- Chromium/real PostgreSQL18 + Garage: A encrypts a sensitive original JPEG; B publishes independently signed ECDH exchange directory. A prepares opaque blackout while warm offline, opts-in and encrypts a separate JPEG into existing Local-First outbox; syncs both. A pins B fingerprint, confirms `safe_read` recipient grant, B pins A, verifies signature/receipts, decrypts *only* the new JPEG. Test black inner/red outer pixels, no private metadata inheritance, no original manifest or chunks from B, grant domain binding, revoke with 410, and intact A original.
- **Not completed:** public anonymous safe-card delivery, safe video/audio, independent owner visual safety approval, recipient original key rotation/retroactive erasure, native Safari/iOS/Android and owner release acceptance. Never merge/deploy/change `main` without owner consent. Matrix and physical GC remain paused/OFF.
