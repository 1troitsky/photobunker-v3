# P2 Safe / Original — signed owner editorial Safe Photo ↔ Assignment binding

**Status:** Draft / independent private verification only. Parent #109 passed exact-head 6/6 CI, 40/40 Chromium, 242/242 Vitest, 138/138 PHPUnit. Absolutely NO public link, anonymous token, media key, public metadata result or publication.

## What the owner can actually certify

A PB3 assignment's owner may explicitly attach **their own** source Photo MediaFile and **their own distinct blackened/E2EE Safe JPEG MediaFile** to **their own** signed assignment. The owner signs the exact triple of IDs and the immutable SHA-256 hashes of both MediaFile contracts and the original root assignment contract with a unique `pb3.safe-assignment-editorial-link.v1\n` signature. This is a server-verifiable **editorial association**, never proof that a third-party contributor took the photograph or completed the assignment.

**Critical restriction:** P2 photo capture/submissions by another account are NOT covered. Legacy `assignment_submissions_v1` references `photo_records` rather than P2 MediaFiles. New `assignment_media_submissions_v1` is video/audio only. A contributor-owned original + owner-owned assignment must not gain editorial or public rights from matching an ID alone. Future P2 contributor submissions require a *separate contributor-signed provenance/consent contract*, independently validated role, deadline, account exchange and owner authorization.

## Contract, source and expiration

- Signed canonical body: `version=1, linkId, operationId, ownerAccountId, assignmentId, sourceMediaId, safeMediaId, sourceContractHash, safeContractHash, assignmentRootHash, expiresAt`. All UUIDs/hashes strict. Both MediaFiles must be distinct, synchronized, active, unarchived, **photo**, owned by exactly the signing account, and not expired. Assignment must have the same owner, valid immutable owner-signed root and open file retention.
- Before creating a link, the server verifies both independently signed preview ceiling histories from #108 and #109: **all revisions** in consecutive SHA-256 hash chains, signatures, ownership, IDs, file hashes, root assignment hash, current head, TTL and forced `publication=disabled`, `actions(view,copy,download,share)=false`. A plain client's declared assignment ID or local folder is never enough.
- `GET /media-file-preview/v1/assignment-links/{safeMediaId}` is **owner-authenticated only**. It rechecks at every read current signatures/hashes of the link, both MediaFiles, assignment and both preview policies, live archive/TTL/retention and returns only signed association ID/hash/body and the mathematical boolean `candidateFields = assignmentFields AND fileFields`. `effectivePublicFields` is **ALWAYS seven FALSE values**, regardless of any true candidate field; `linked=true` does not imply any recipient grant, public token or permission. No private GPS/description/tag values travel through this API.
- POST create serializes on the owner account and locks assignment/media/association records, accepts a single immutable link per Safe MediaFile. Exact-byte replay is idempotent; different assignment, source, signature or hash for the same Safe ID fails closed (409).
- Owner may sign an explicit `pb3.safe-assignment-editorial-detach.v1\n` with `version,operationId,linkId,ownerAccountId,safeMediaId,linkContractHash,action='detach'`. After detach, reads return 410 and no new link for that Safe file is allowed in v1; signed audit remains. The independent original/derivative media, retention, E2EE recipient grants and past downloads are unchanged. Rollback refuses to drop any signed history.
- Browser stores only ID/hash/signature/boolean fields in an account-scoped Dexie retry outbox. It verifies the owner-signed server receipt before claiming `sent`; offline queued work is never represented as a cloud ACK. UI says **«Связать с моим заданием»**, not «Выполнено задание». Owner explicitly confirms bind and detach. No public URL is generated.
